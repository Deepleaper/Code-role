# Code-role Genuine Star Growth Plan / 真实 Star 增长计划

Stars are a lagging signal. The leading signal is whether a developer understands Code-role, initializes it, completes one real milestone loop, and can explain what became more predictable.

Star 是滞后指标。真正的领先指标是：开发者是否看懂 Code-role、完成初始化、走完一个真实 milestone 闭环，并能说明哪里因此变得更可控。

## 30-Day Outcome / 30 天目标

| Metric | Target | Evidence |
| --- | ---: | --- |
| Design partners who try a real milestone | 10 | Named private/public feedback records |
| Successful Minimal Profile initializations | 5 | User-confirmed `--check` pass or reproducible issue |
| Public worked examples or case notes | 3 | Discussion, article, or repository link |
| High-signal Issues/Discussions | 5 | Reproducible workflow evidence |
| Genuine GitHub stars | 30 | GitHub repository count |

The first 30 stars should come from people who understand the problem, not purchased accounts or reciprocal-star campaigns.

前 30 个 Star 应来自真正理解问题的人，而不是购买账号或互刷活动。

## Conversion Funnel / 转化路径

1. **Discover:** a concrete claim reaches a developer who has experienced AI coding drift.
2. **Understand:** the README explains the category and difference in 30 seconds.
3. **Verify:** the visitor inspects the worked example or runs the 60-second initializer.
4. **Adopt:** the visitor controls one real milestone.
5. **Contribute:** the user shares evidence, opens a focused issue, or improves a template.
6. **Star:** the user bookmarks a project they now expect to reuse.

Each promotion asset should move the reader one step forward. A post that only asks for a star is a failed asset.

## Phase 1: Proof Before Launch / 第一阶段：先建立可信证据

Duration: days 1-7.

- Recruit 5-10 design partners from teams already using Codex or another coding agent.
- Ask each partner to use the four-workstation profile on one bounded milestone.
- Record only three questions:
  1. Where did an agent previously claim completion too early?
  2. Which Code-role field removed the ambiguity?
  3. Where did the role still have to guess?
- Turn the strongest sanitized result into one repository Discussion and one worked example.
- Fix onboarding defects before broad distribution.

Exit condition: at least three users outside the maintainer's own projects can initialize the profile and explain the PM/evaluator split correctly.

## Phase 2: Coordinated Public Launch / 第二阶段：集中公开发布

Duration: days 8-10.

Launch within one 48-hour window:

1. Publish GitHub Release `v0.4.0` with the OKR-delivery refactor and verified test evidence.
2. Post a technical `Show HN` with the problem, design tradeoff, and repository link.
3. Launch on Product Hunt with a short demo and a candid first comment.
4. Publish one bilingual technical article showing an actual milestone before and after Code-role.
5. Share the same evidence, adapted to the norms of each community; do not cross-post identical promotional text everywhere.

Respond to every substantive question with implementation detail. Do not ask friends to create empty comments or artificial engagement.

## Phase 3: Compounding Distribution / 第三阶段：形成长期复利

Duration: days 11-30 and ongoing.

- Ship one evidence-backed example or release note each week.
- Submit Code-role to relevant curated lists only after the repository meets their contribution rules.
- Add integrations only when a real user needs them; do not add logos without working support.
- Convert repeated support questions into a shorter guide, validator, or issue template.
- Invite maintainers of complementary projects to critique the workflow boundary, not to exchange stars.
- Keep Discussions active with monthly "milestone evidence clinic" threads.

## Channel Strategy / 渠道策略

| Channel | Best asset | Goal |
| --- | --- | --- |
| GitHub README and Release | 60-second start, worked example, changelog | Convert repository visits |
| Show HN | Technical design story and tradeoffs | Reach engineering early adopters |
| Product Hunt | Clear demo and use-case framing | Reach tool explorers |
| Technical article | Before/after milestone evidence | Build search and trust |
| GitHub Discussions | Real workflow reports | Retain users and improve product |
| Relevant agent/coding communities | Reproducible lesson, not an ad | Find design partners |

Always read and follow each community's self-promotion rules before posting.

## Weekly Scorecard / 每周复盘

| Question | Binary result |
| --- | ---: |
| Did at least one new user complete initialization? | 0/1 |
| Did at least one user attempt a real milestone? | 0/1 |
| Did we publish one new piece of verifiable evidence? | 0/1 |
| Did we resolve the top onboarding failure? | 0/1 |
| Did stars come from genuine discovery rather than solicitation? | 0/1 |

If stars rise but real milestone attempts do not, promotion is attracting the wrong audience.

## Integrity Rules / 增长底线

- Never buy stars.
- Never use star-for-star exchanges.
- Never automate GitHub accounts, comments, or reactions.
- Never overstate runtime automation: Code-role is a local role-control workflow.
- Never describe an example as independently proven unless the evidence exists.
- Never hide the process cost of the Full Profile; recommend the Minimal Profile by default.
