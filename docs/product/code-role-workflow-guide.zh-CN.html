Code-role / Codex Software Delivery Control

Code-role：四角色最小单元，八角色完整交付

Code-role 用明确责任、结果型 KR、单一主交付物、客观证据和独立评估控制 Codex 编程交付。 它提供两套正式配置：四角色最小版用于快速、完整的目标闭环；八角色完整版用于复杂、高风险和需要完整审计的工程交付。

适用对象：个人开发者、技术创始人、工程负责人和 AI 工程工作流设计者。

1. 为什么需要 Code-role

直接让 Codex 在一个对话里同时完成需求、架构、代码、测试和 review，最常见的问题不是“不会写”，而是目标不断漂移： 每个阶段都产出了内容，但没有人对最终里程碑负责；实现自报成功，评估口径又随着结果变化。

Code-role 不把更多流程当成目标。它只保留能够提高交付确定性的控制点：谁负责目标、谁负责专业结论、怎样证明完成、谁独立评估。

共同原则：项目经理定义完整项目 OKR，产品定义覆盖整个里程碑的完整产品契约，只有工程可以拆分执行 STEP；实现不能自我验收，必需证据未获得就是未完成。
交付 KR 必须是可观测的用户、业务、产品或运行时结果。调研、PRD、架构、评估 SOP、测试、报告、packet 和 review 只是方法或证据，不是交付 KR。

2. 两套正式配置

四角色与八角色不是新旧版本，也不是高低等级。它们是同一产品针对不同任务复杂度提供的两种流程深度。

四角色最小版

Minimal Profile

完整控制一个软件 milestone 所需的最小责任单元。

  • 一份里程碑作战板作为唯一权威。
  • 项目经理维护完整 KR-*，产品维护完整 KR-*，工程内部拆分 STEP-*。
  • 项目经理、产品策略、工程、独立评估。
  • 产品、工程、评估各有角色专属任务书、一份必需主交付物与短回报，不使用 packet 链。
  • 适合产品方向较清楚、范围可控的持续迭代。

八角色完整版

Full Profile

把研究、产品、架构、上下文、实现、评估和审计拆成独立专业责任。

  • Orchestrator 精简状态与已接受主交付物是当前权威链路。
  • 每个专业角色都有专属任务书、一份必需主交付物和短回报契约。
  • Test Evaluator 与 Reviewer 分别负责评估和最终审计。
  • packet、manifest 和 lock 仅在需要不可变审计时可选启用。
  • 适合复杂、高风险、研究密集或需要审计追溯的 milestone。
同一个 milestone 只能有一套活跃控制模型。不能一边用四角色的 milestone-board.md 路由，一边又让八角色 packet 状态决定进度。

3. 如何选择

判断问题 选择四角色最小版 选择八角色完整版
产品含义 已经明确，或产品策略工位可以一次解决。 需要独立研究和 PRD 多轮收敛。
架构风险 可作为工程工位中的一种工作模式处理。 架构契约必须在代码映射和实现前独立确认。
证据追溯 一份作战板和专业附件足够。 必须保留独立专业主交付物；版本化 packet 可选用于审计。
评估与审计 完整工程候选物产生后，由独立评估工位记录可执行 SOP 并完成复评。 Test Evaluator 与 Reviewer 需要职责分离。
流程成本 需要更快启动和更少手动传递。 愿意用更多流程换取更强专业隔离和审计。

最简单的选择规则：如果把某个专业环节合并进工程工位会丢失重要判断或审计证据，就使用八角色完整版；否则从四角色最小版开始。

4. 四角色最小版

项目经理与用户定义唯一的 Project Objective 与 KR-1...KR-N，控制全局交付阶段，并依据独立证据关闭里程碑。
产品策略在同一组 KR 下补全 Product Contract，明确用户价值、产品行为、范围、阈值、非目标和 claim boundary，不创建第二套 OKR。
工程消费项目 OKR 与 Product Contract，自主拆成 STEP-1...STEP-N，完成必要研究、架构、实现、测试和完整可运行候选物。
独立评估只在完整候选物产生后启动，记录可执行 SOP，并独立验证所有 KR。
完整项目 OKR用户确认一个 Objective 和完整二值 KR-* 集合。
完整产品契约产品一次性覆盖全部 KR，不把 KR 一个个派给工程。
工程候选物工程自主拆分 STEP，直到完整可运行候选物与可复现证据都存在。
独立证据评估师验证完整 KR，项目经理只依据独立证据更新 KR。

软件交付始终围绕同一套 KR，顺序固定为“项目 OKR -> 产品契约 -> 工程 STEP 与候选物 -> 独立评估 -> 项目经理决策”。评估不能出现在产品之后、工程之前。

5. 八角色完整版

Workflow Orchestrator控制 milestone、权威状态、路由和关闭。
Researcher整理仓库证据、外部研究、风险与未知项。
Product / PRD定义产品价值、范围、验收和 claim boundary。
Architect定义架构契约、边界、接口、数据流和风险。
Code Context映射精确文件、函数、字段、测试、artifact 和实现约束。
Implementer修改被批准的业务文件，并提交实现与验证证据。
Test Evaluator依据冻结 SOP 独立执行完整评估。
Reviewer从 Orchestrator 开始审计所有最终角色产物是否偏离原始 milestone。

每个专业角色完成后先返回 Orchestrator。Orchestrator 检查同一组 KR 的产品覆盖、工程候选物门禁、任务书验收检查与客观证据，再推进全局交付阶段。专业结论来自角色主交付物，不由 Orchestrator 自行改写；聊天格式、packet 状态和 lock 不构成日常完成门禁。 

Workflow Orchestrator
  -> Researcher -> Workflow Orchestrator
  -> Product / PRD -> Workflow Orchestrator
  -> Architect -> Workflow Orchestrator
  -> Code Context -> Workflow Orchestrator
  -> Implementer -> Workflow Orchestrator
  -> Test Evaluator -> Workflow Orchestrator
  -> Reviewer -> Workflow Orchestrator

6. 初始化到具体项目

6.1 获取 Code-role

git clone https://github.com/Deepleaper/Code-role.git
cd Code-role

6.2 初始化四角色最小版

python scripts/init_loop_workflow.py "/absolute/path/to/project" \
  --project-name "Project Name"

同步新规则且保留现有作战板和专业附件：

python scripts/init_loop_workflow.py "/absolute/path/to/project" \
  --project-name "Project Name" \
  --sync

校验：

python scripts/init_loop_workflow.py "/absolute/path/to/project" --check

6.3 初始化八角色完整版

先预览：

python scripts/init_project_workflow.py \
  --target "/absolute/path/to/project" \
  --project-name "Project Name" \
  --initial-milestone workflow-bootstrap \
  --initial-chain full-chain

确认后写入：

python scripts/init_project_workflow.py \
  --target "/absolute/path/to/project" \
  --project-name "Project Name" \
  --initial-milestone workflow-bootstrap \
  --initial-chain full-chain \
  --write
两套初始化器都只生成本地角色控制文件，不修改业务源码。如果目标目录已经是 Git 仓库，会把 code-role/ 加入本地 .git/info/exclude。

7. 日常控制方法

四角色最小版

  1. 在项目经理对话中确认唯一的 Project Objective、KR-*、非目标和独立证据。
  2. 项目经理把同一组 KR 交给产品，产品在这些 KR 下补全 Product Contract，不创建第二套 OKR。
  3. 产品契约整体通过后，项目经理把项目 OKR 与 Product Contract 交给工程；工程自行拆分 STEP 并交付完整可运行候选物。
  4. 只有候选物门禁通过后，项目经理才向独立评估下发覆盖全部 KR 的评估任务书。
  5. 评估师返回独立结果；项目经理据此关闭里程碑，或把失败契约退回产品/工程修正。

八角色完整版

  1. Orchestrator 与用户确认唯一的 Project Objective、KR-* 与权威输入。
  2. Researcher、Product / PRD、Architect、Code Context 分别围绕同一项目 OKR 工作；Product / PRD 必须在现有 KR 下补全 Product Contract。
  3. Implementer 消费完整全局契约，自行拆分 STEP，产出完整可运行候选物与可复现证据。
  4. 候选物门禁通过后，Test Evaluator 才独立评估所有 KR；Reviewer 最终审计完整链路与阶段顺序。
  5. 每个角色用专属短回报返回 Orchestrator，不选择下一角色；Orchestrator 只推进全局阶段，不改写专业结论。

当前两套配置都使用人工可复制传递，不声称已自动跨对话派发。

两套配置共用同一对话控制：启动确认消息为 0，常规过程汇报为 0，格式返工为 0；只有实质 blocker 或用户决策才增加对话轮次。

8. 完成与证据

  • 0：必需结果尚未获得独立证据。
  • 1：所有冻结通过条件都有可接受证据。
  • 必需检查未运行就是 0。
  • 残余问题必须成为新要求、明确非目标，或保持未解决状态。
  • partial_pass 和 pass_with_residual_risk 不能关闭 milestone。
  • 只有项目经理更新 milestone 状态。
“更接近完成”“方向正确”“基本可用”都不是完成状态。完成声明必须指向具体条件、观察结果和独立证据。

9. Git 与发布边界

Code-role 不接管目标项目原有 Git 流程，也不为普通 Git 操作建立第二套审批链。

  • 产品代码仍按目标项目原有方式 branch、commit、review、merge 和 release。
  • 目标项目中的 code-role/ 默认是 local-only 辅助。
  • code-role/ 不是产品 runtime、客户交付包、CLI payload 或 release artifact。
  • Code-role 模板仓库自身可以正常提交和发布。
Target project code-role/:
local role-control assistance
not product runtime
not product delivery
not committed by default
Code-role 的目的不是把流程做重，而是让流程深度与风险匹配：四角色保证最小完整性，八角色保证专业拆分和完整审计。
