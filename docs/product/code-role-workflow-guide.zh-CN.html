Code-role 工作流说明与项目初始化指南

这份文档解释 Code-role 是怎么来的、解决什么问题、每个角色怎么协作，以及如何把它快速初始化到一个具体项目里。

适用对象：想用 Codex 做复杂编程交付，但希望每一步先讨论、再确认、再执行的个人开发者、技术负责人和 AI 工作流设计者。

1. 它是怎么来的 2. 它是什么，不是什么 3. 八个角色 4. Packet 与交接 5. 工作链路 6. 初始化到项目 7. 实际运行流程 8. Git 与发布边界 9. 常见问题

1. 它是怎么来的

Code-role 来自一个很具体的工程问题：直接让 Codex 在一个聊天里完成需求分析、架构设计、代码实现、测试和 review，短期看很快，长期看很难稳定交付。

常见问题包括：需求还没确认就开始写代码；架构假设留在聊天里；实现范围不断漂移；测试标准不清；review 只能看结果，追溯不到为什么这么做。

Code-role 的做法是把 Codex 编程过程拆成多个专业角色，每个角色只产出自己的文件化结果。用户先和这个角色讨论，确认后再进入下一个角色。这样流程不是自动化流水线，而是一个可审计、可讨论、可回退的工程控制层。

核心原则：聊天可以用于讨论，但不能作为事实源。事实源必须落在文档、manifest、lock、状态文件和 Git 记录里。

2. 它是什么，不是什么

Code-role 是什么

  • 本地角色配置项目。
  • 讨论优先的 Codex 工作流模板。
  • 用文档 packet 控制复杂编程任务的过程层。
  • 让每个角色有明确输入、输出和边界。
  • 让实现、测试、review 都能追溯上游依据。

Code-role 不是什么

  • 不是多 Agent 自动执行平台。
  • 不是让 Codex 一路自动写到底。
  • 不是 GitHub、Jira、Linear 或 IDE 替代品。
  • 不是产品运行时内容。
  • 不是默认要进入客户交付包的内容。

推荐使用模型： 

Code-role 项目 = 角色定义、workflow 协议、初始化脚本
目标业务项目 = 实际被分析、讨论或修改的代码仓库

3. 八个角色

Code-role 推荐一个角色一个 Codex 对话。这样做不是为了增加仪式感，而是为了隔离职责和上下文。

角色 职责 是否能改代码
Workflow Orchestrator 流程总控。判断 milestone、chain、权威 packet、下一角色、是否可消费。 不能。
Researcher 只做事实调研、证据地图、风险和开放问题。 不能。
Product / PRD 把研究输入转成需求范围、验收标准、非目标和产品决策。 不能。
Architect 定义架构边界、接口、数据流、测试策略和架构风险。 不能。
Code Context 映射代码影响范围、依赖、测试入口和实现约束。 不能。
Implementer 在明确授权的文件范围内实现改动，并写实现记录。 可以，但必须先获批。
Test Evaluator 评估测试计划、测试结果、回归矩阵和质量门禁。 不能。
Reviewer 审查最终链路、gap、残余风险和是否允许进入下一阶段。 不能。

每个角色都有自己的 ROLE.md，启动时必须读取自己的角色定义。角色不能靠聊天记忆猜自己该做什么。

4. Packet 与交接

每个执行角色的产出都是一个版本化 packet。packet 是一个文件夹，里面包含该角色的正文文档和 handoff.manifest.json。 

code-role/workflow/roles/product-prd/reports/<milestone>/packet-v001/
  product-brief.md
  prd.md
  acceptance-criteria.md
  non-goals.md
  decision-log.md
  handoff.manifest.json

handoff.manifest.json 是下游角色的入口。它记录这个 packet 属于哪个角色、是什么状态、包含哪些文档、消费了哪些上游 packet、是否阻塞、是否允许下游消费。

packet 从 draft 开始。只有用户确认后，角色才能把它标记为 ready_for_next_role，并创建 packet.lock.json 记录 manifest 和正文文档的 hash。下游角色正式消费时，Orchestrator 要先校验这些 hash。

不允许下游角色扫描“最新文件”来猜输入。必须由 Orchestrator 或用户提供精确的 upstream manifest 路径。

5. 工作链路

不同任务不需要同样重的流程。Code-role 用 chain 控制流程长度。

Chain 适用场景
full-chain 新功能、复杂重构、安全/权限/运行时相关变更。
mini-chain 范围较清楚，但仍需要架构和代码上下文的任务。
patch-chain 小修复、小文档治理、小范围实现。
docs-only-chain 只改文档，不进入实现。
research-only 只做调研，不进入 PRD、架构或实现。

6. 初始化到具体项目

以前初始化一个项目需要手动创建 code-role/、角色 prompt、Orchestrator 状态和索引文件。现在可以用初始化脚本一次生成基础配置。

6.1 准备 Code-role 项目

git clone https://github.com/Deepleaper/Code-role.git
cd Code-role

6.2 在目标项目中生成配置

python scripts/init_project_workflow.py \
  --target "/path/to/Target Project" \
  --project-name "Target Project" \
  --tracking repo-tracked \
  --initial-milestone workflow-bootstrap \
  --initial-chain research-only \
  --write

如果只是预览会生成哪些文件，可以去掉 --write。

6.3 tracking policy 怎么选

策略 含义 适用场景
repo-tracked code-role/ 作为仓库治理基础设施，可以进入 Git 历史。 团队要共享审计链、角色配置和工作流记录。
local-only code-role/ 只作为本地协作记录，不进入仓库。 个人临时使用，或不希望工作流文件进入项目历史。
无论选择哪种策略，code-role/ 都不是产品运行时内容，不应进入模板索引、客户交付包、CLI payload 或 release artifact，除非项目负责人明确批准。

6.4 初始化后会生成什么

初始化脚本不会创建 Researcher、PRD、Architect、Implementer 等执行角色 packet。执行角色 packet 必须由对应角色在用户确认后创建。

7. 实际运行流程

  1. 打开 Workflow Orchestrator 的 Codex 对话。
  2. 粘贴目标项目里的 code-role/role-instance-prompts/workflow-orchestrator.md。
  3. 让 Orchestrator 恢复状态，确认第一个真实 milestone 和 chain。
  4. Orchestrator 输出下一个角色和精确 upstream manifest。
  5. 为下一个角色打开新的 Codex 对话。
  6. 粘贴对应的 code-role/role-instance-prompts/<role>.md。
  7. 角色先确认读取范围、写入范围和禁止范围。
  8. 用户回复“开始”后，角色创建 draft packet。
  9. Orchestrator 消费 draft，判断是否可进入 readiness。
  10. 用户确认后，角色标记 ready_for_next_role 并创建 packet.lock.json。
  11. Orchestrator 校验 ready packet，再路由下一个角色。

state-index 的作用

code-role/state-index/ 是角色接入索引。它告诉新角色当前项目走到哪一步、该读什么、不能读什么、当前残余风险是什么。

它不是新的事实来源。如果 state-index 和 manifest、packet.lock 或 Orchestrator 状态冲突，必须以后者为准。

8. Git 与发布边界

Code-role 把 Git 操作视为单独授权的动作。任何角色都不能自动执行 git add、git commit 或 git push。

8.1 推荐 Git 流程

  1. Orchestrator 或执行对话先给 staging plan。
  2. 明确列出要 stage 的文件和要排除的 dirty files。
  3. 用户确认后才执行 git add。
  4. 查看 staged diff。
  5. 用户确认 commit message 后才执行 git commit。
  6. 用户确认后才执行 git push。

8.2 发布物边界

code-role/ 可以在明确批准后进入 Git 历史，作为仓库治理和审计记录。但它不等于产品发布内容。 

code-role/ is repo-tracked governance infrastructure.
It is not product runtime content.
It must be excluded from generated template indexes, customer delivery bundles, CLI template payloads, and release artifacts unless explicitly approved.

9. 常见问题

必须一个角色一个对话吗？

推荐这样做。它能强隔离职责，减少上下文污染，也符合“每一步先讨论再执行”的目标。初始化脚本会生成每个角色的启动 prompt，降低手动配置成本。

能不能让 Codex 自动跑完整链路？

不建议。Code-role 的目标不是自动化跑完，而是控制质量和边界。每个状态转换、实现开始、Git 操作都需要用户确认。

packet 为什么要 lock？

因为下游角色需要知道自己消费的是哪个精确版本。packet.lock.json 记录 manifest 和正文文档的 hash，防止上游 packet 被悄悄改写。

state-index 会不会变成新的事实源？

不会。它只是导航索引。权威永远是 Orchestrator 状态文件、handoff.manifest.json 和 packet.lock.json。

新项目最快怎么开始？

克隆 Code-role，运行 scripts/init_project_workflow.py，打开 Orchestrator 对话并粘贴生成的启动 prompt。之后每个角色都使用目标项目里生成的对应 prompt。

Code-role 是讨论优先的本地角色工作流模板。它的重点不是替代工程判断，而是让 Codex 的工程过程更可控、更可追溯、更容易和人讨论。
