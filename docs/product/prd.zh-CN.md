# Code-role 产品需求文档

## 1. 产品定义

Code-role 是一个用于控制 Codex 编程交付的本地角色系统。

它把一个软件里程碑转化为明确责任、专业产物、客观完成证据和独立评估。它不替代工程判断、Git、IDE 或项目管理工具。

Code-role 正式提供两套产品配置：

1. **四角色最小版：** 能完整控制一个里程碑的最小单元。
2. **八角色完整版：** 将专业职责进一步拆分，并使用版本化 packet 证据和最终链路审计。

两套配置都不是旧版。它们以不同流程深度解决同一个交付控制问题。

## 2. 产品原则

产品围绕“里程碑是否完成”组织，而不是围绕“角色做了多少事情”组织。

角色写了文档、修改了代码或运行了命令，都不等于完成。只有已确认通过条件获得客观证据，并由指定独立评估角色验证后，所需结果才算完成。

两套配置共同遵守：

- 项目经理对里程碑负责。
- 专业角色对专业结论负责。
- 接受工作前必须明确完成条件。
- 缺少必需证据就是未完成，不使用模糊的部分完成。
- 实现不能自我验收。
- 聊天只是交互界面，不是权威项目状态。
- 目标项目生成的 `code-role/` 是本地辅助，不是产品运行时或发布内容。

## 3. 要解决的问题

AI 编程交付常见四类失败：

1. **目标漂移：** 角色优化自己的即时产出，而不是已确认的 milestone。
2. **职责漂移：** 产品、架构、实现、评估和审计结论混在一起。
3. **证据漂移：** 把活动或自报成功误当成独立验证的完成证据。
4. **流程过载：** 对小任务强制太多阶段，却没有提高质量。

单一流程深度无法同时解决“流程过重”和“高风险可追溯”两类问题，因此 Code-role 提供四角色最小单元和八角色完整配置。

## 4. 目标用户

主要用户：

- 使用 Codex 完成非简单软件任务的个人开发者。
- 需要稳定 AI 编程交付的技术创始人。
- 建立可复用 AI 工程规范的技术负责人。
- 希望加强产品与评估纪律、但不想引入工作流 SaaS 的小团队。

次要用户：

- AI 工作流设计者。
- 负责高风险、基准敏感或需要完整审计的软件项目团队。

## 5. 双配置模型

### 5.1 四角色最小版

四角色最小版保留完整交付控制所必需的四种责任：

- 一个对结果负责的项目经理；
- 明确的产品判断；
- 专业工程执行；
- 独立评估。

| 工位 | 负责内容 |
| --- | --- |
| 项目经理 | Objective、二值 KR、当前 KR、路由、迭代预算、证据接受和 milestone 关闭 |
| 产品策略 | 用户价值、产品行为、范围、阈值、非目标和 claim boundary |
| 工程 | 工程研究、必要架构、必要代码上下文映射、实现、测试和候选证据 |
| 独立评估 | 评估基线、数据集、grader、命令、阈值、目标检查、回归检查和二值观察结果 |

四角色最小版使用：

- 一份权威 `milestone-board.md`；
- 一份固定项目经理任务书；
- 每个专业工位一份固定回报模板；
- `code-role/work/<milestone>/` 下的专业附件；
- 每轮只围绕一个已确认 `KR=0` 动态路由。

它不要求 packet、manifest、readiness 转换、lock 或固定角色链。

### 5.2 八角色完整版

当职责拆分能够实质降低不确定性或风险时，使用八角色完整版。

八角色完整版要求每个角色分别配置一个独立角色实例。每个角色使用自己的对话并消费明确上游文档，不做一个对话内的多角色自动切换。

八个角色：

1. Workflow Orchestrator / 项目经理
2. Researcher / 研究员
3. Product / PRD / 产品经理
4. Architect / 架构师
5. Code Context / 上下文工程师
6. Implementer / 实现工程师
7. Test Evaluator / 测试评估师
8. Reviewer / 复核审计

八角色完整版使用：

- 已确认的 milestone contract；
- Orchestrator 状态和路由；
- 分角色版本化 packets；
- 精确上游 `handoff.manifest.json`；
- 二值角色完成契约；
- 冻结的 evaluation SOP；
- 需要不可变证据时可选严格 packet lock；
- Reviewer 对 Orchestrator 及所有角色当前最终产物的完整审计。

八角色完整版支持 `full-chain`、`mini-chain`、`patch-chain`、`docs-only-chain` 和 `research-only`，但每个专业角色完成后都必须先返回 Orchestrator，再决定下一角色。

## 6. 配置选择规则

项目经理在 milestone 启动时提出配置建议，由用户确认。

以下情况使用四角色最小版：

- 产品含义已经明确，或可由产品策略一次解决；
- 架构和代码上下文可以作为工程模式处理；
- 一份里程碑作战板足以作为权威；
- packet 级追溯增加的成本高于实际风险降低。

以下情况使用八角色完整版：

- 外部研究和仓库研究需要独立责任；
- 架构决策需要在代码映射前独立审阅；
- 实现范围广或涉及安全关键边界；
- 多份证据 packet 需要长期可检查；
- 独立评估和最终 milestone 漂移审计需要不同责任人；
- 监管、客户、benchmark 或发布声明要求更强审计链。

同一 milestone 中不要静默切换配置。切换必须包含：

1. 明确原因；
2. 状态映射方案；
3. 用户确认；
4. 切换后只保留一套权威控制模型。

## 7. 功能需求

### FR-1：二值里程碑定义

- 项目经理定义一个 Objective。
- 默认不超过五个可观察 Key Results。
- 每个 KR 都有通过条件和必需独立证据。
- 每个 KR 只能是 `0` 或 `1`。

### FR-2：每轮一个交付目标

- 每轮只针对一个已确认 `KR=0`。
- 可以回归其他 KR，但不能暗中把它们变成新的交付目标。
- 项目经理记录当前 owner 和迭代次数。

### FR-3：专业责任

- 项目经理不发明、不重写专业结论。
- 每个专业角色都有固定输入和固定回报契约。
- 详细专业推理存放在角色拥有的附件中。
- 缺少必需专业字段的回报不可接受。

### FR-4：独立评估

- 优化开始前冻结评估条件、数据、grader、环境、命令和阈值。
- 评估完整 milestone 必需范围，不只评估最新 diff。
- 指定时必须同时运行目标能力检查和回归检查。
- 必需检查未运行就是 `0`。
- 工程或 Implementer 不能自行判定 KR 通过。

### FR-5：失败闭环

- 评估失败必须提供观察证据，并在可确定时指出可执行 owner。
- 项目经理把失败路由给产品、工程或评估定义修复。
- 四角色最小版默认同一 KR 最多三次失败的“工程到独立评估”尝试，之后必须停止并重构问题。
- 八角色完整版通过 packet 和 Orchestrator 状态记录失败尝试。

### FR-6：本地初始化

- `scripts/init_loop_workflow.py` 初始化四角色最小版。
- `scripts/init_project_workflow.py` 初始化八角色完整版。
- 两个脚本都只生成本地角色控制材料，不修改业务源码。
- 如果目标已经是 Git 仓库，两者都通过本地 `.git/info/exclude` 排除 `code-role/`。

### FR-7：配置校验

- 最小版校验必须确认恰好四个活跃提示词、必需模板、二值目标闭环和独立评估契约。
- 完整版校验覆盖角色提示词、工作流协议、source map、packet schema 和角色完成门禁。
- 仓库测试必须阻止文档和生成提示契约发生漂移。

## 8. 非目标

Code-role 不做：

- 自动跨 Codex 对话派发任务；
- 自主运行多 Agent 编程流水线；
- 不做一个对话内的多角色自动切换；
- 替代 GitHub、IDE、任务管理、CI 或发布管理；
- 把 `code-role/` 变成目标产品运行时；
- 强制每个 milestone 都使用八个角色；
- 允许四角色流程绕过产品定义或独立评估；
- 把定性进度写成 milestone 完成；
- 自动批准 merge、deploy、publish、delete、payment 或生产环境变更。

## 9. 成功标准

产品成功必须满足：

1. 用户不需要猜哪一套才是“当前版本”，就能选择正确配置。
2. 新项目可通过一条明确命令完成初始化。
3. 每个活跃角色都知道自己的专业输入、输出、权限和停止条件。
4. 项目经理能根据客观证据判断 milestone 状态。
5. 独立评估不依赖 Implementer 判断即可复现必需检查。
6. 每次交接都让下一角色少一个需要猜测的问题。
7. 小型 milestone 可使用最小版而不承担 packet 开销。
8. 复杂 milestone 可使用完整版而不丢失专业和审计追溯。

## 10. 质量标准

Code-role 应减少：

- 跳过需求；
- 范围漂移；
- 无证据完成声明；
- 评估基线漂移；
- 超出确认范围的实现；
- 对决策原因的人工重建。

Code-role 不应增加：

- 没有风险收益的角色数量；
- 没有下游决策 owner 的文档；
- 与产品证据无关的流程门禁；
- 额外 Git 或发布仪式。

## 11. 正式产品产物

当前正式产物：

- 顶层中英文 README 与配置选择说明。
- 四角色最小版协议、四个提示词、流转模板、初始化器和测试。
- 八角色完整版协议、八个角色定义、角色输出标准、packet 模板、初始化器、校验器和测试。
- 中英文 PRD。
- 可外发的中文 HTML 初始化指南。
- 最小项目示例。

## 12. 近期迭代

1. 为两套配置各补一个完整示例 milestone。
2. 在生成的项目经理提示词中加入配置选择检查表。
3. 在单 packet 校验之外补充八角色完整链路校验。
4. 在真实项目中记录配置时间、迭代次数、错误声明率和评估复现率。
5. 只有手动传递稳定、透明后，才增加可选自动派发。
